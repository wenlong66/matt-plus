# 生产 UI 工程

## 目标

将已确认的产品与设计决策落实为可维护、可访问、能处理真实状态的 UI。优先使用项目已有的 token、组件、路由、数据获取和测试方式；不要为了一个页面引入第二套设计系统或状态管理框架。

详细验收项目见 [无障碍检查表](../../references/accessibility-checklist.md)。

## 开始前

1. 阅读相关 `DESIGN.md`、组件库、样式约定和相邻实现。
2. 明确页面的用户目标、数据来源、权限、空数据、加载失败、提交失败和成功反馈。
3. 识别技术栈。React、Tailwind 和任何示例库都只是可替换示例，不是安装指令。
4. 如果设计缺失或冲突，停止猜测品牌方向，交给 `design-consultation` 或请用户决定。

## 实现原则

### 结构与状态

- 让表现组件围绕一个清晰职责组织；只在真实重复或复杂状态出现时拆 hook/文件。
- 将远程数据、URL 可分享状态、局部交互状态和跨应用状态放在已有架构最合适的位置。不要因传参层数或文件行数达到某个数字就机械换 context/store。
- 在调用数据前处理 loading、empty、error、permission-denied 和 partial-data 状态。每个状态给用户下一步，而非空白屏。
- 提交和乐观更新必须有 rollback 或重新获取策略；失败信息不泄露内部错误。

### 设计系统

- 使用语义 token、既有间距/排版/圆角尺度和已批准的组件变体，避免任意像素、原始色值和临时阴影。
- 内容优先：使用真实或有代表性的文本、长度和数据，而不是掩盖溢出与层级问题的占位内容。
- 避免通用的紫色渐变、无意义卡片网格、过度圆角、巨大留白、装饰性阴影和只为“看起来像 AI”而添加的效果。
- 视觉变化应保留信息优先级：重要操作、错误、风险和辅助信息不能只靠颜色区分。

### 可访问性与响应式

- 使用原生语义元素；按钮、链接、输入和列表不能用可点击 `div` 冒充。
- 给无可见文字的操作提供可访问名称；每个输入有程序可识别的标签和关联错误。
- 对 modal、popover、异步内容和路由切换管理焦点。不要把“将焦点放到关闭按钮”误称为 focus trap：若使用对话框，优先项目已有已验证组件或实现完整的 tab 循环、Escape、返回触发元素和背景隔离。
- 同时检查键盘、焦点可见性、读屏语义、缩放、reduced motion、颜色对比和触控尺寸。
- 从窄视口开始，用真实断点和内容压力检验布局，至少检查 320px、768px、1024px、1440px 或项目定义的等价尺寸。

## 工作流

1. **读现状**：找相邻页面、可复用组件、设计 token、数据/错误约定及既有测试。
2. **列出状态契约**：在修改前写明正常、loading、empty、error、无权限、成功与不可用交互如何呈现。
3. **最小实现**：只改任务相关文件，组合已有组件而非堆叠可配置 props。
4. **验证**：运行项目已有的相关检查；在可用浏览器中做与本次实现直接相关的键盘、视口、console 和状态检查。没有运行环境时明确 `UNVERIFIED`。
5. **交付**：说明 UI 行为、被覆盖状态、检查结果及未验证项。完整功能/回归浏览器 QA 转交 `web-qa`；运行中页面的视觉一致性问题转交 `design-review`。

## 验收

- [ ] 页面遵循已有 `DESIGN.md` 或组件系统。
- [ ] 正常、loading、empty、error 与权限状态都对用户有意义。
- [ ] 所有交互可用键盘完成且焦点顺序合理。
- [ ] 图标按钮、输入、错误和动态结果拥有正确语义。
- [ ] 窄到宽视口没有溢出、遮挡或不可达操作。
- [ ] 未安装新 UI 库、未改动无关样式，也未把静态审查说成浏览器验收。
